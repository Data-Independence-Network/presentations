## 🧭 Послайдовая структура (15 слайдов)

1. **Слайд 01: Титульный слайд — Архитектурный профиль узла «Лист» (Leaf)**
   - Назначение: Манифест суверенного локального хранилища: превращение клиентского устройства в полноценный отказоустойчивый сервер данных.
   - Визуальный чертеж: Анатомия узла «Лист» (Среда приложений $\to$ Механизм виртуализации $\to$ Ядро SQLite `WITHOUT ROWID` $\to$ Flash NVMe).

2. **Слайд 02: Парадигма Single RDBMS против фрагментации хранилищ**
   - Проблема: Антипаттерн разделения данных на тысячи файлов SQLite `.db` (исчерпание дескрипторов, невозможность кросс-базовых JOIN, фрагментация блокировок).
   - Инженерное решение: Единая высокопроизводительная реляционная СУБД на клиенте, разделенная на виртуальные репозитории на уровне схемы.

3. **Слайд 03: Виртуализация репозиториев внутри единого пространства**
   - Концепция: Репозиторий как логический криптографический сейф внутри монолитной базы данных.
   - Механика: Локальные целочисленные идентификаторы (`LID`) для сжатия ключей и сопоставление с глобальными 128-битными `GUID`.

4. **Слайд 04: Триада первичного ключа: Глобальная уникальность без координатора**
   - Инвариант: Базовый первичный ключ любой суверенной сущности `AirEntity`: `(REPOSITORY_LID, ACTOR_LID, ACTOR_RECORD_ID)`.
   - Математическое свойство: Полное исключение конфликтов при одновременной генерации записей миллионами отключенных от сети узлов.

5. **Слайд 05: Семантика сущности «Актор» (Actor)**
   - Определение: Триада ответственности `Actor` = «Идентификатор пользователя + Устройство/Лист + Конкретное приложение».
   - Механика: Локальный целочисленный счетчик `_actorRecordId`, работающий в памяти без глобальных блокировок и распределенного консенсуса.

6. **Слайд 06: Физическая кластеризация страниц: Механизм WITHOUT ROWID**
   - Инженерия: Использование структуры `WITHOUT ROWID` в SQLite с кластерным первичным ключом.
   - Выигрыш: Физическое упорядочивание строк по `REPOSITORY_LID` — все данные одного репозитория располагаются последовательно на 4КБ страницах диска.

7. **Слайд 07: Топология внешних связей: Тройные составные внешние ключи**
   - Архитектура: Тройные реляционные связи `{entity}_RID_`, `{entity}_AID_`, `{entity}_ARID_`.
   - Надежность: Обеспечение строгой ссылочной целостности (Referential Integrity) между таблицами локальной СУБД на аппаратном уровне ядра SQLite.

8. **Слайд 08: Паттерн сущностей-мостов (Bridge Entities)**
   - Проблема: Риск разрушения суверенитета репозитория при прямых связях с внешними хранилищами (например, Задача в проекте $\to$ Цель в стратегии).
   - Решение: Промежуточная сущность-мост (`GoalTask`, `CollectionConversation`), хранящаяся внутри ссылающегося репозитория.

9. **Слайд 09: Детерминированный глобальный адрес: 11-сегментный eGUID**
   - Спецификация: Формат расширенного идентификатора `${repository.GUID}-${actor.GUID}-${_actorRecordId}`.
   - Преимущество: Мгновенный синтаксический парсинг адреса любой сущности в глобальной сети без выполнения сетевых запросов и поиска по индексам.

10. **Слайд 10: Пятиуровневый иерархический WAL (Transaction History)**
    - Структура журнала: `TransactionHistory` $\to$ `RepositoryTransactionHistory` $\to$ `OperationHistory` $\to$ `RecordHistory` $\to$ `New/Old Values`.
    - Назначение: Гранулярный аудит на уровне колонок, позволяющий вычленять изменения конкретного репозитория для передачи по сети.

11. **Слайд 11: Сетевой блок синхронизации (`RepositoryBlock`)**
    - Архитектура: Формирование криптографического пакета синхронизации для репликации в P2P-сети.
    - Безопасность: Хэш-цепочка изменений (Merkle-срез) и двойная электронная подпись (автора записи и штампа времени узла).

12. **Слайд 12: Двухэтапный процессор синхронизации (Two-Stage Sync Processor)**
    - Этап 1 (Stage 1): Конфликт-резолюция версий, проверка подписей и упорядочивание графа изменений (DAG).
    - Этап 2 (Stage 2): Трансляция внешних GUID в локальные LID и атомарная запись в локальные таблицы SQLite.

13. **Слайд 13: Полиморфизм приватности: Механизм Anti-Linkability**
    - Угроза: Профилирование пользователя по постоянному открытому идентификатору при публикации транзакций в общих репозиториях.
    - Защита: Динамическая ротация псевдонимов актора и ротация связок ключей (`Keyring v1` $\to$ `v2`), исключающая корреляцию метаданных.

14. **Слайд 14: Суверенное «Право на забвение» (Right to Be Forgotten)**
    - Двойной механизм:
      1. Криптографическое уничтожение мастер-ключа репозитория (делает распределенные копии WAL навсегда нечитаемым белым шумом).
      2. Физический `VACUUM` локальной базы SQLite для гарантированного затирания секторов флеш-памяти.

15. **Слайд 15: Архитектурное резюме узла «Лист»**
    - Итог: «Лист» как математически неуязвимый сейф первичных данных гражданина и бизнеса.
    - Мост к следующему выпуску: Как прикладной каркас (Framework) и песочница обеспечивают доступ к этим данным без риска утечек.
