## 🧭 Послайдовая структура (15 слайдов)

1. **Слайд 01: Титульный слайд — Архитектура узла «Ветка» (Branch Node)**
   - Назначение: Манифест промежуточного координатора: обеспечение гарантированной доставки, локализация трафика и хранение без дешифрования.
   - Визуальный чертеж: Место Ветки в топологии (Сотни узлов Лист $\to$ Конвейер Ветки $\to$ Родительская Ветвь / Ствол).

2. **Слайд 02: Роль узла «Ветка» в распределенной топологии**
   - Назначение: Локализация 80% сетевого трафика внутри района или предприятия, буферизация сообщений для временно отключенных узлов (Mailbox).
   - Инвариант: Нулевой доступ к содержимому приватных сейфов (Zero-Knowledge Relay).

3. **Слайд 03: Трехфазный конвейер обработки данных (3-Phase Pipeline)**
   - Инженерия: Архитектурная цепочка `PersistentQueue` (диск) $\to$ `ConcurrentMap` (ОЗУ) $\to$ `FileSystem` (архив).
   - Смысл: Развязка скорости приема (Ingestion), скорости раздачи (Serving) и долговременного хранения (Retention).

4. **Слайд 04: Фаза 1 — Персистентная очередь WAL (PersistentQueue)**
   - Надежность: Атомарная фиксация входящих пакетов `RepositoryBlock` с вызовом `fsync` на диск.
   - Скорость: Моментальная выдача подтверждения приема (ACK) клиенту менее чем за 2 миллисекунды.

5. **Слайд 05: Фаза 2 — Параллельная карта памяти (ConcurrentMap)**
   - Оптимизация: Безблокировочная структура данных в оперативной памяти (Lock-Free Concurrent SkipList/Hash Map).
   - Назначение: Удержание горячего окна последних транзакций для мгновенной отдачи пирам без чтения с диска.

6. **Слайд 06: Фаза 3 — Сегментный архив логов (FileSystem / Append-Only)**
   - Хранилище: Сброс блоков из памяти в сегментированные файлы журналов (Append-Only Segments).
   - Устойчивость: Линейная запись на диск, исключающая фрагментацию файловой системы и обеспечивающая легкое резервное копирование.

7. **Слайд 07: Горячая синхронизация (Hot-Sync): Потоковая репликация**
   - Протокол: Потоковая рассылка дельт подписанным активным узлам в реальном времени прямо из `ConcurrentMap` в оперативной памяти.
   - Характеристики: Минимальные задержки (<5 мс) и нулевая нагрузка на дисковую подсистему.

8. **Слайд 08: Холодная синхронизация (Catch-up Sync): Возврат из офлайна**
   - Сценарий: Узел подключился после длительного отключения и запрашивает историю с блока N.
   - Механика: Автоматическое каскадирование запроса: поиск в ОЗУ `ConcurrentMap` $\to$ чтение сегментов `FileSystem` $\to$ потоковая отдача.

9. **Слайд 09: Механизм Time-Traveling: Путешествие во времени**
   - Возможность: Воспроизведение состояния любого хранилища на произвольный исторический момент времени $t$.
   - Алгоритм: Применение детерминированной последовательности изменений $S_t = S_0 + \sum \Delta_i$ по неизменяемым журналам транзакций.

10. **Слайд 10: Управление жизненным циклом и Pruning (Очистка логов)**
    - Вызов: Неограниченный рост журналов транзакций со временем.
    - Решение: Механизм безопасного прунинга (Pruning) устаревших дельт после фиксации согласованного снапшота состояния.

11. **Слайд 11: Снапшоты состояния хранилищ (State Snapshots)**
    - Архитектура: Периодическая фиксация базового снимка состояния хранилища, подписанного кворумом участников.
    - Эффект: Ускорение холодного старта новых устройств: загрузка одного компактного снапшота вместо воспроизведения миллионов старых дельт.

12. **Слайд 12: База общественных данных (PublicData)**
    - Назначение: Обслуживание открытых муниципальных реестров, районных досок объявлений, каталогов товаров и голосований.
    - Механика: В отличие от приватных зашифрованных сейфов, данные `PublicData` индексируются Веткой для быстрого открытого поиска.

13. **Слайд 13: Изоляция контекстов безопасности: Приватные сейфы vs PublicData**
    - Разграничение: Строгая архитектурная изоляция: общественные реестры доступны для чтения и аналитики Ветки, приватные хранилища остаются непроницаемыми шифр-блоками.
    - Гарантия 152-ФЗ: Оператор Ветки физически не имеет ключей для расшифровки приватных данных жителей.

14. **Слайд 14: Катастрофоустойчивость и бенчмарки пропускной способности**
    - Метрики: Сравнение легковесного конвейера Ветки с тяжелыми кластерами Kafka/Cassandra на одинаковом типовом оборудовании.
    - Результаты: 50 000+ транзакций/сек на скромном 8-ядерном сервере при потреблении менее 2 ГБ ОЗУ.

15. **Слайд 15: Архитектурное резюме узла «Ветка»**
    - Итог: «Ветка» как надежный периферийный буфер и районный координатор без риска утечки персональных данных.
    - Мост к следующему выпуску: Сетевая маршрутизация, WebRTC P2P-соединения и сквозные туннели к ведомствам.
